## TASK-015 — cleanup markers atomic, non-fatal (r3, Option A)

### MUST-CHANGE

**015-M1. "Oversized" quarantine silently drops a committed erase on large journals.**
The writer has no size limit (`write_new(&marker, …)`, deletion.rs:291). The reader rejects more than 1 MiB (deletion.rs:330).
One `Attachment` entry is about 211 bytes of JSON (uuid id, `screenshots/<uuid>.webp`, size, sha256). So a marker for about **4,970 or more attachments** goes over 1 MiB. A heavy user can reach that: there are at most 20 screenshots per review (attachments.rs:35), and no journal-wide cap. Whole-journal and account erase previews do not limit the attachment count (dump caps database pages, not rows). TASK-014 exists so that large journals *can* be erased.
- Today such a marker gives `LimitExceeded`, then `cleanup_pending`, then OpenFailed on every start.
- Under r3 step 3 it is **quarantined**, and its listed screenshots and recovery copies are never removed. The user was told the journal was erased, but `data-controls/*` (which holds `safety.db` with the full pre-erase journal) and the screenshots stay on disk. That is a privacy regression hidden behind a "Ready" status.
- Fix: never quarantine a marker that parses. Either derive the reader limit from the writer's maximum (or enforce the same limit at write time, before commit), or stream-parse it. Quarantine only bytes that cannot be parsed or entries that are not regular files. Add a test with a marker over 1 MiB that is valid.

**015-M2. `prepare_restore` must still refuse while a well-formed committed cleanup is pending.**
Step 7 ("cover both call sites") plus step 5 (non-fatal) allows restore prepare to go ahead past a *pending* whole-journal cleanup, for example one held up by an antivirus lock.
- After the restore installs, the next `recover_cleanup` sees `erase_operation` ≠ marker id (deletion.rs:358). It skips the recovery-copy removal and then **deletes the marker** (:382).
- The pre-erase recovery copies the user asked to erase are then orphaned for good, and no status ever shows it.
- Today the `?` at runtime.rs:230 blocks restore until the cleanup completes.
- Fix: the spec should say that only quarantined (unparseable) markers stop blocking restore prepare, and that a pending well-formed marker still returns `RecoveryRequired`. Add a test.

### SHOULD-CHANGE

**015-S1. Define what `recover_cleanup` returns.** Three callers depend on its `Err` meaning "something is still pending":
- `execute` maps it to `completed`/`cleanup_pending` (deletion.rs:309).
- `retry_data_cleanup` (commands.rs:643) passes it through.
- The dialog shows "File cleanup finished" on `Ok` (DeletionDialog.tsx:72-75).

If an implementer makes step 5 "non-fatal" inside `recover_cleanup`, erase reports `completed` and the retry toast is wrong. Test tests.rs:580 catches only part of this. The spec should say: keep `Err` (or an explicit pending result) whenever any marker remains or anything was quarantined, and make the non-fatal mapping in `runtime.rs` only. It should also say to keep processing the remaining markers after one fails (today the loop exits on the first `?`).

**015-S2. Option A status lifecycle is unspecified.**
- `RuntimeProvider` stops polling once ready (RuntimeProvider.tsx:58).
- `begin_initialize` returns false when Ready (runtime.rs:261), so `retry_runtime` cannot re-run cleanup.
- The new field is set at startup, but nothing says who updates it after `retry_data_cleanup` or `permanently_delete_data`.
- `commands.rs` and a Runtime setter are missing from the scope list. Without them, the banner either stays "pending" after a successful retry or never appears for a pending cleanup created in-session.
- Add: Rust updates the field on those commands, the frontend re-fetches status after them, and a test covers it.

**015-S3. The quarantine move itself.**
- On Windows (sharing violation from antivirus) or on any IO error, a failed move must also be non-fatal. Today step 3 only covers the marker's content.
- `std::fs::rename` replaces an existing target on both Windows (MoveFileEx `REPLACE_EXISTING`) and Unix, so a name collision in `data-controls-quarantine/` would silently overwrite an earlier quarantined file. Use a no-clobber move with a unique suffix.
- For the marker publish, the existing `publish()` (filesystem.rs:505-510: sync, `persist_noclobber`, sync parent) fits better than copying `write_pending`'s overwriting `persist`. The destination UUID name must never already exist.

**015-S4. Add a Windows-deterministic lock test.** The antivirus-lock path is only an "optional manual check in TASK-032". Add a `#[cfg(windows)]` cargo test that holds the listed file open with `share_mode(0)`, then asserts Ready, cleanup pending, and nothing deleted. CI already runs on `windows-latest`.

### NIT
- `sync_dir` does nothing on Windows (filesystem.rs:494-504), so "sync both directories" gives no durability there. State this; optionally use `MOVEFILE_WRITE_THROUGH`.
- `NamedTempFile` names (`.tmpXXXX`) left in the data root by a crash are never swept (same as `write_pending`). Use a recognisable prefix so whole-journal erase or TASK-018 can include them.
- Step 6 says a quarantined marker means its "listed files remain as strays". This is mostly inaccurate: the marker is fsynced before the database commit, so a truncated marker implies no commit, and the files are still owned.

### TASK-019
- `store/reviews.rs:530` `(entry - stop).abs()` and `domain.rs:410` `(exit - t.entry_price)` are the only unchecked Decimal price subtractions in src (grep).
- Experiment (rust_decimal 1.43.0): `MAX.checked_sub(-1)` gives `None`; `4e28 - (-4e28)` gives `None`; `MAX - (-1)` **panics "Subtraction overflowed"**. Fractional operands round instead of overflowing. Overflow needs integer magnitudes of about 4e28 or more with opposite signs. That is never realistic. It is reachable only by typed, imported or restored garbage. Prices have no sign or bound check (`domain.rs:309-316`, `reviews.rs:227-236`), so `entry=-1` is accepted.
- Effect: the release profile unwinds (`Cargo.toml:46`), and `runtime.rs:191-192` recovers a poisoned lock, so only the command fails (ISSUE-015 notes the invoke may hang). The save path **commits first** (`reviews.rs:506`) and then calls `get` → `derived_risk` → panic. So the save is persisted but the UI sees a failure (an uncertain outcome), and every later `get_trade_review` and the whole Insights dataset (`insights.rs:220`) panic. Pulling it into W1 is justified.
- TS side: no TS computes P&L or planned risk. `ReviewCard.tsx:72,83` passes strings through and displays Rust's figure. `packages.md:158-160` lists realized P&L as "still Rust-only". **No parity fixture is needed.** The change leaves every in-range output unchanged, so `trade-contract.json` is not regenerated, which matches the fixture rule.
- `rederive_account` runs inside the account-update transaction (`accounts.rs:321-324`). It runs on a currency **or timezone or reset** change.

## Findings

### TASK-018
**M-018-1 (MUST-CHANGE): an AC that cannot be met as written.** "Every app-owned path listed in the scope … uses the root-anchored check" lists `fundedflow.db` (+`-wal`/`-shm`/`-journal`), `fundedflow.db.before-v*.bak`, `legal-acceptance.json` and `attachments/`. None of these goes through `no_symlink_components` today:
- SQLite opens the database and creates WAL/SHM itself.
- The backup is at `db/mod.rs:246`, and there is also an unlisted `previous-*.bak` at `:273`.
- `legal.rs:84` and `store/attachments.rs:204/262/302` have their own `symlink_metadata` checks.

Meeting the AC literally means adding new link checks to the SQLite open path and the legal and attachment writers. That is unreviewed scope on a "High (startup)" risk task, and `-wal`/`-shm` cannot be checked before SQLite creates them. Reword it to "every **existing** `no_symlink_components` call site on an app-owned path is switched". List the paths that are not covered today (database files, backups, the legal record, attachment writes in `store/attachments.rs`) and either record them as a Triage card or add them explicitly with tests.

**S-018-1 (SHOULD-CHANGE): `write_new` (`filesystem.rs:117`) serves both kinds of path, so the 21/3 split is wrong for it.** Archive export calls `write_new(temp/data.json)` in a `tempdir_in(<user-chosen parent>)` (`archive.rs:229, 243`). It also calls `export_csv(&csv_path)` there (`:245` → `:552`). Other callers are app paths: `deletion.rs:291`, `restore.rs:134/138/196`, `archive.rs:386`. A root-anchored `write_new` has no app root for the export call. Passing the temp dir as the "root" would quietly relax the user-path check that the card says must stay. The spec should require separate functions (anchored for app paths, full-walk for user paths) and name `archive.rs:243/245` as user-path uses.

**S-018-2 (SHOULD-CHANGE): reparse-tag semantics.** Step 3 rejects "only IO_REPARSE_TAG_SYMLINK / MOUNT_POINT". The safer and simpler rule is to reject any **name-surrogate** tag, which is exactly std `is_symlink()`. That also covers LX_SYMLINK (WSL symlinks), WCI_LINK and future surrogates without windows-sys. State the rule: below the anchor, remove the `0x400` test and keep `is_symlink()`. Volume mount points carry the MOUNT_POINT tag, so they are treated like junctions.

**S-018-3 (SHOULD-CHANGE): no stated policy for cloud and sync folders.** Today, any 0x400 attribute (including OneDrive Files On-Demand cloud tags) on the app folder or above it blocks startup. That accidentally keeps a SQLite WAL journal out of sync and placeholder folders, where it can be dehydrated or corrupted. After the relaxation, "Roaming junctioned into OneDrive/Dropbox" starts Ready. The spec should decide explicitly: allow it, refuse it with its own message, or warn. A cloud tag (IO_REPARSE_TAG_CLOUD_*, non-surrogate) on the root or the db file would pass step 3 unnoticed. A related case: "redirected Roaming" in the case list is ambiguous. Folder Redirection to a UNC share is not a reparse point at all, and WIN-011 calls a network WAL unsupported. Define the manual case as local-path redirection, and mark UNC as out of scope (WIN-011).

**S-018-4 (SHOULD-CHANGE): the anchor must fail closed.** Require the anchored check to return `UnsafePath` when `path.strip_prefix(root)` fails, so a mistaken call cannot skip checks. Compare lexically. Do **not** `canonicalize` (or `dunce::canonicalize`) the root: canonicalisation resolves the very junctions being checked and adds `\\?\` prefixes that break the prefix comparison. Also drop the current behaviour of stopping silently on a metadata error *at or below* the root: a component that exists but cannot be read should fail.

**S-018-5 (SHOULD-CHANGE): no regression test for a link inside the data folder.** The Safety section says "must not allow a junction inside the data folder", but step 5 and the ACs test only "parent is a junction" (Ready) and "root is a junction" (refused). Add `cfg(windows)` tests where `attachments/` or `data-controls-cleanup/` is a junction → refused. Also say how tests create junctions: `cmd /C mklink /J` needs no admin rights. A `junction` dev-dependency would trigger the dependency-approval rule.

**S-018-6 (SHOULD-CHANGE): the TASK-011(b) prerequisite.** TASK-018 is Release-Blocking: Yes, and the defect is Confirmed from code alone. Making an owner-run VM measurement of the *pre-fix* behaviour a hard prerequisite only adds schedule risk. TASK-018's own manual AC already re-runs every case on the fixed build. Make 011(b) an input, not a blocker. If it stays a blocker, align the case lists (see S-011-2).

**N-018-1 (NIT):** Spell out the category mapping for startup `recover`/`recover_cleanup` failures caused by `UnsafePath` (`runtime.rs:335, 352`), as well as for `filesystem_ownership`. Also split Busy (keep OpenFailed, retryable) from UnsafePath (new category, not retryable). Mirror the `runtime.ts` invariant for `newer_schema` (no retry).

**Security judgment:** relaxing the check above `app_data_dir()` does **not** reopen a real attack. Ancestors of `%APPDATA%` are writable only by the user or administrators. An attacker with those rights can already change the journal directly. The original check matters for following links planted *inside* the app folder: recursive delete or restore writing outside it. That protection is kept as long as S-018-1/4/5 are handled.

### TASK-019
**S-019-1 (SHOULD-CHANGE): test preconditions.** The planned-risk subtraction runs only after `instrument.filter(|i| i.currency == currency)` (`reviews.rs:528`). The test must use a symbol that resolves to an instrument in the account currency (for example ES with a USD account). Otherwise it passes before the fix and the AC "panic before the change" cannot be shown. **S-019-2 (SHOULD-CHANGE): rederive and Insights.**

After the fix it still blocks, but with `AppError::invalid("exitPrice", "P&L is too large to store")`, rolled back inside the transaction (`accounts.rs:321-324`). Saturating arithmetic would invent money and is wrong. Silently storing `None` P&L for a manual entry would hide bad input. "Optional, P2" is reasonable because the magnitudes are unrealistic. W1 inclusion (already approved) is justified by the commit-then-panic save and the Insights-wide failure. No TS/Rust parity work is needed.
