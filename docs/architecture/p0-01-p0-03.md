## 1. P0-01: fill-pair identity

### Defect

`csv_import/dedup.rs` keyed paired-fill rows `fills:{buy}:{sell}`. Fill IDs may contain `:` (`check_id` allows
letters, digits, `- _ . :`), so `(a:b, c)` and `(a, b:c)` both produced `fills:a:b:c`. The second distinct trade was
skipped as a duplicate (in one file or a later import), and a deleted trade could be restored by the wrong pair.

### Encoding decision (identity version 2)

New fill-pair trades are stored under

```
fills2:<n>:<buyFillId>:<sellFillId>        n = byte length of buyFillId in UTF-8, decimal, no leading zeros
```

- **Collision-free:** the length fixes where the buy ID ends, so the key decodes to exactly one `(buy, sell)`
  for any strings, including IDs with `:`. Nothing is escaped, so supported IDs appear verbatim.
- **Deterministic:** depends only on the two normalized IDs (as validated by `check_id`, unchanged).
- **Versioned:** the `fills2:` prefix can't be produced by any legacy key (`fills:`, `id:`, `rt:`).
- **Unchanged:** `id:<trade id>` (broker trade ID) and `rt:<sha256>` (fallback) keys and their inputs.

`dedup::fill_pair_key` is the only writer; `dedup::legacy_fill_pair_key` exists only to read old journals.
Examples (also asserted in tests): `("a:b","c")` → `fills2:3:a:b:c`; `("a","b:c")` → `fills2:1:a:b:c`;
`("707776450007","707776450023")` → `fills2:12:707776450007:707776450023`.

### Compatibility decision for existing journals

`trades.dedup_key` is immutable (migration 1 trigger) and unique per account, and shipped migrations must not change,
so **no migration** rewrites keys and no historical row is edited. Instead, classification (`dedup::classify`,
shared by preview and commit) looks a pair up in this order:

1. The account's trade with the `fills2` key → exact match.
2. Otherwise, the account's trade with the legacy key `fills:<buy>:<sell>`, joined to its stored
   `trade_round_trips` row:
   - stored `buy_fill_id`/`sell_fill_id` equal this pair exactly → that trade (duplicate, or restore of the same
     trade ID);
   - stored pair present but different → a different trade that collided; this row is **new** and is stored under
     its `fills2` key (no unique-key conflict with the legacy key);
   - no stored round trip, or a missing fill ID → **ambiguous**: the row is reported `invalid` with an `identity`
     error ("Couldn't tell whether this row is already saved … add this one by hand if it is missing") and is
     neither imported, restored nor linked. Later copies in the same file are equally ambiguous.

The legacy key is never split on `:`; only stored source fill pairs decide. Account scope applies to every lookup.

Consequences: exact repeats of legacy imports still deduplicate (after reopen too); a pair the earlier release
skipped because of a collision now imports on re-import, under a new trade ID; earlier `import_rows` keep their
recorded status and `duplicate_of_trade_id` (including a link the old collision recorded), because provenance is
never rewritten. `Duplicate.key` / `Restore.key` in the preview carry the row's `fills2` identity even when the
matched trade is stored under a legacy key.

### Transactions and revalidation

Unchanged authority: preview writes nothing; commit re-runs analysis and classification inside its
`BEGIN IMMEDIATE` transaction, then writes the batch, every row, restores and inserts together or rolls back. The
target-assessment preview token binds the classification (now including ambiguous rows), so a change between
preview and commit requires a fresh preview. There is no migration to roll back.

### Coordination with P0-04 (not done here)

The TypeScript domain has no CSV normalization or dedup algorithm, so there is nothing to change on the TS side.
A future portable normalizer (P0-04) must produce the `fills2` key exactly as above (UTF-8 byte length, not UTF-16
`length`) and must leave the legacy lookup to the Rust/SQLite repository, which owns stored round trips. The golden
fixture's `dedupKeys` are the parity target. Portable extraction and any parity claim stay with P0-04.

## 2. P0-03: uncertain-write recovery

### Pattern (unchanged, reused)

The shared submission coordinator (`features/shared/submissions.ts`) keeps an `uncertain` scope locked;
`useFeatureMutation().checkUncertainOutcome(read)` re-reads with throwing refreshes and never resends;
`UncertainOutcomeReview` runs Check result → stored-record review → "I've checked; allow saving again", disabled
until the original request has settled and the review reads have loaded. Acknowledging only releases the lock. No
coordinator, hook or design-system change was needed. The QueryClient-owned coordinator survives closing a dialog,
leaving a route and a render crash (Build 26.5), so recovery is available without a restart.

### Lock scopes traced, and what each review reads

| Surface | Mutation (repository) | Lock scope | Review reads (all re-read by Check result) | Where the review shows |
|---|---|---|---|---|
| Rulebook draft save | `rulebooks.updateDraft` | `["rulebook", accountId]`, shared with discard, publish/verify, start draft, assign | the version as saved now (state, last saved, rule count, reason) + the account's recent rulebook activity | draft editor save bar |
| Rulebook publish / verify (and discard) | `rulebooks.publish` / `discardDraft` | same | same as above | publish panel, also once the version became read-only |
| Rulebook assignment | `rulebooks.assign` | same | the account's assignments as saved now + activity | assign dialog |
| Start draft | `rulebooks.createDraft` | same | versions of the target rulebook (catalogue, or the account's own once it exists) + activity | start-draft dialog |
| Calculation | `snapshots.save` via `calculateNow` | `["risk-calculation", accountId]` | the account's saved calculations, newest first, and whether one was saved after this request | Calculate now (rulebook page and Today's Calculate estimate) |
| Today checkpoints / comparisons | `evidence.create` / `evidence.reconcile` | `["evidence", accountId]` | stored checkpoints and comparisons, newest first, and whether the entered checkpoint is among them | Verify balance dialog, both steps |
| Screenshots (add / remove) | `reviews.addScreenshot` / `removeScreenshot` | `["screenshot", accountId, tradeId]` | the trade's stored screenshots: name, size, attached time (no file location) | trade review Screenshots section |

Because the rulebook scope is shared, any of those screens can release an uncertain rulebook write; the account's
activity log shows which write was recorded. Review text uses stored values and fixed copy only: no raw backend
error, path or SQL.

Behaviour details fixed on the way:

- A publish or discard that did save makes the panel read-only; the review now stays in the same place there.
- After a reviewed draft save that did save, the editor adopts the stored draft when it equals the form, instead of
  reporting "changed somewhere else"; otherwise the edits stay unsaved in the form.
- The publish/discard confirmation and the screenshot problem list say an uncertain write *may* have been saved and
  to check below, instead of "couldn't be saved"; the remove-screenshot confirmation says it may have been removed.
- Pasting a screenshot while its scope is locked sends nothing (the dropzone was already disabled).
- Daily review keeps its existing (acknowledge-then-show) behaviour; import, account and manual-trade recovery are
  unchanged.

### P0-03 acceptance → tests (jsdom, `apps/desktop/src/journeys/uncertain-writes-p0.journey.test.tsx`)

One `describe.each` runs the same six cases against each of the seven surfaces' real wiring (42 tests), plus four
surface-specific journeys (46 total). Holds decide whether the write ran (`lose`) or not (`fail`) and when it answers.
Against the previous production code 41 of the 46 fail (the account-isolation cases pass there, as the old lock was
already scoped per account).

| Acceptance | Case (each surface) |
|---|---|
| Did save, answer lost | "did save but the answer was lost…": review lists the stored record, still locked until acknowledged, no second write, no success message |
| Did not save | "did not save…": review shows nothing stored, edits kept, one deliberate save after acknowledging |
| Failed check, successful recheck | "keeps the lock when the check fails…": both read attempts fail, no acknowledge, Check again recovers, nothing resent |
| Late completion, lock while running | "can't be acknowledged while the original request still runs…": fake timers past the 30 s timeout, acknowledge disabled, late success claims nothing and does not unlock |
| Close/reopen, recovery without restart | "keeps the lock after closing and reopening the surface…" |
| Account isolation | "locks only this account…": the other account's same write proceeds |
| Preserved edits / selection | asserted in the not-saved and failed-check cases (draft reason, publish note, assignment reason, start-draft reason, calculation fee coverage selection, checkpoint amount, review notes) |
| No duplicate write | every case asserts the held write was called once |
| Shared rulebook lock | an uncertain draft save is released from the assignment dialog via the activity review; a reviewed saved draft is adopted without a false conflict |
| Comparison and screenshot removal | dedicated journeys |

Existing account/manual-trade/import/daily-review journeys and crash-recovery tests still pass unchanged.
